# 技术架构

## 1. 总体数据流

```text
数据源/用户文件
      ↓
  ingest（导入）
      ↓
normalize（规范化）
      ↓
validate（校验与质量报告）
      ↓
dedupe（确定性去重）
      ↓
analysis（统计分析）
      ↓
report（Markdown/JSON/CSV）
      ↓
dashboard（本地可视化）
```

每一层都应有明确输入和输出，避免把网络访问、文本清洗、统计计算和展示逻辑混在一起。

## 2. 模块边界

当前原型已经包含以下模块，后续按边界逐步扩展：

- `models`：职位记录、质量问题、数据集和报告结果的数据结构。
- `io`：CSV/JSON 读写以及文件级元数据。
- `normalize`：文本、城市、学历、日期、薪资和技能规范化。
- `quality`：必填字段、数值、日期、URL 和薪资范围校验。
- `dedupe`：基于规范化字段的确定性指纹和重复记录诊断。
- `analysis`：薪资、城市、技能和基础分组统计。
- `report`：Markdown 和 JSON 序列化。
- `dashboard`：单文件 HTML/CSS/JavaScript 仪表盘生成，不依赖外部资源。
- `sources`：本地文件适配器、来源许可和访问方式元数据。
- `cli`：命令行参数、错误展示和退出码。

计划新增或细化：

- 公开 API 适配器：仅在明确授权、许可和访问边界后增加。

## 3. 技术选择

- Python `>=3.10`，保持核心运行路径简单、可测试。
- 现阶段核心依赖优先使用 Python 标准库，减少安装和离线运行障碍。
- 当前可视化使用单文件 HTML/CSS/JavaScript，保证离线演示和低部署成本；后续如需复杂交互，再评估 Streamlit 与 Plotly 可选依赖。
- 当需要持久化多次导入的数据集时，优先考虑 SQLite，而不是立即引入远程数据库。
- GitHub Actions 用于测试、类型检查、构建和发布前校验。
- 文本输出和 schema 变更需要在变更日志中记录。

## 4. 关键设计原则

### 数据来源无关

核心分析只接收规范化记录，不依赖某一个招聘网站的页面结构或接口。

### 来源优先

记录来源、采集时间、许可和处理版本。报告应能说明“这份数字基于什么数据”。

### 离线优先

导入本地文件后，校验、分析和报告生成不需要联网。在线适配器是可选边界。

### 确定性

相同输入和配置应得到等价输出。排序、去重和缺失值处理不能依赖未定义的遍历顺序。

### 隐私意识

默认只处理职位级数据。任何可能包含个人信息的字段都不属于公开 schema。

### 可解释错误

错误信息应包括文件、行号、字段名和修复方向；不能只抛出无法定位的异常。

## 5. 错误处理策略

- 文件不存在、格式无法解析、必填字段缺失：命令失败并返回非零退出码。
- 单条记录字段无效：记录错误，默认跳过该记录；报告中保留质量摘要。
- 可接受但不完整的数据：记录警告并继续分析。
- 分析没有可用样本：生成明确的空结果或返回可读错误，不能输出伪造的零值。
- 数据源网络错误：由适配器返回带来源上下文的错误，核心分析不重试网络请求。

## 6. 版本与兼容性

- Python 包采用语义化版本。
- 输入 schema 的破坏性变更必须提升主版本或提供迁移说明。
- 报告 JSON 的顶层字段应保持稳定，并包含 `schema_version`。
- 分析算法变化如果会改变历史结果，应在变更日志中说明并增加固定 fixture。

## 7. 性能目标

MVP 目标是在普通个人电脑上对本地 10 万条以内的职位记录完成一次 CLI 分析，并保持内存使用可接受。实际基准将在数据质量和去重模块完成后建立，不以未经测量的数字作为稳定承诺。

## 8. 安全边界

- 凭证通过环境变量或本地未提交配置提供，不写入代码、日志和报告。
- 数据源适配器必须显式声明访问方式和用户授权前提。
- 不实现绕过登录、验证码、频率限制或访问控制的逻辑。
- 所有外部输入都按不可信数据处理，尤其是 URL、文本和文件路径。
